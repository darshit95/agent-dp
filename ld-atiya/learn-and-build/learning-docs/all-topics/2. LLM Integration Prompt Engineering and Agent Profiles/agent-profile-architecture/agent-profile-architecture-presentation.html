The Problem: Generalist vs Specialist

Monolithic generalist agent:

  • Single profile tries to handle all failure types
  • Jack of all trades, master of none
  • Accuracy: 72% (mediocre across the board)

Example: PARTS test failures

  • Network issues (BGP, IPsec, routing): 72% accuracy
  • Config issues (policies, NAT, zones): 72% accuracy
  • Timing issues (timeouts, races): 72% accuracy
  • Resource issues (memory, CPU): 72% accuracy

The insight: A dermatologist is better at skin problems than a general practitioner

Speaker Notes

The fundamental problem is diluted expertise. When you train one agent to handle everything, it becomes mediocre at everything. For Atiya, we're diagnosing 1000+ PARTS test failures per day across network failures (BGP session flaps, IPsec timeouts), config failures (NAT policy mismatches, zone errors), timing failures (test timeouts, race conditions), and resource failures (memory leaks, connection pool exhaustion). A single generalist achieves 72% accuracy because it applies the same reasoning to all failure modes. A network specialist who deeply understands routing protocols can achieve 94% accuracy by applying network-specific debugging methodology.

Speaker Notes

Multi-specialist architecture is the team of experts pattern. Instead of one generalist, we have multiple specialists, each world-class in their narrow domain. The architecture has two layers: 1) Coordinator layer routes incoming failures to the appropriate specialist based on failure characteristics. 2) Specialist layer where each specialist has deep expertise in their domain. Network specialist (94% accuracy on network failures) knows routing protocols, VPN technologies, tunnel debugging. Config specialist (96%) knows zone policies, NAT rules, security profiles. The 22pp accuracy gain comes from specialization - same model (Claude), different profile = different behavior. For Atiya at scale: Network failures 45% of total (450/day) handled by network specialist at 94% accuracy, Config failures 35% (350/day) by config specialist at 96%, yielding weighted average of 91% accuracy.

Profile Structure: The 7 Components

# network_diagnostician_v3.md

## IDENTITY
You are a Network Diagnostic Specialist for PARTS test failures.

## OBJECTIVE
Diagnose network-related failures with 95%+ accuracy.

## EXPERTISE
- Routing protocols (BGP, OSPF, RIP)
- VPN technologies (IPsec, SSL VPN, GlobalProtect)
- Tunnels (GRE, IPsec, monitoring, failover)

## SCOPE
You ONLY diagnose: network.routing, network.vpn, network.tunnel
If NOT network → return OUT_OF_SCOPE

## REASONING PROCEDURE
1. Extract network context
2. Identify failure symptom
3. Trace network path
4. Pinpoint root cause
5. Form diagnosis

## CONSTRAINTS
- ONLY cite evidence from logs/configs
- If out of scope → defer to other specialist

## OUTPUT FORMAT
{JSON schema}

## EXAMPLES
[3-5 network failure examples]

Speaker Notes

A profile is a markdown file that defines an agent's complete behavior. It's like a class definition in OOP - reusable, composable, version-controlled. Each component serves a specific purpose: IDENTITY primes the LLM to think like a network specialist. OBJECTIVE sets success criteria (accuracy, not speed). EXPERTISE is deep domain knowledge (BGP, OSPF, IPsec). SCOPE defines responsibilities (IN_SCOPE: network.routing/vpn/tunnel, OUT_OF_SCOPE: everything else). REASONING PROCEDURE is network-specific debugging methodology (trace packet flow, check routing table). CONSTRAINTS are guardrails (stay in scope, cite evidence only). OUTPUT FORMAT is exact JSON schema. EXAMPLES show how to handle IN_SCOPE, uncertain, and OUT_OF_SCOPE cases. For Atiya, we have 5 profiles (network, config, timing, resource, general), each version controlled in git, independently testable (A/B test v2 vs v3), composable (copy sections from one profile to another).

Profile-versus-Prompt Separation

Mental model:

Profile (System Prompt) = Class definition
Prompt (User Message)   = Method call with arguments

Why separate?

Aspect Profile Prompt Impact
Changes Rarely (v1→v2) Every request Stability
Caching Yes (5min TTL) No 90% cost savings
Size Large OK (5K tokens) Keep concise Profile has expertise
Ownership Curated (Atiya team) Auto-generated Quality control

ROI: $990/month savings from caching alone

Speaker Notes

Profile-versus-prompt separation is a fundamental architectural principle that enables cost optimization through caching. Think of profile as a class definition and prompt as a method call. Profile changes rarely (network_diagnostician_v2 to v3 transition over 2 weeks with 15 iterations and testing, deployed once, affects all future diagnoses). Prompt changes every request (each failure has different logs, configs, test code). Why separate? CACHING - Claude's API caches system prompts with 5-minute TTL. First call: 1500-token profile costs $0.0225, second call (within 5min) costs $0.0023 (10x cheaper). ROI: 1000 diagnoses/day with mixing (profile in prompt) costs $45/day = $1,350/month. With separation (profile in system): $11.70/day = $351/month. Savings: $999/month from caching alone, not even accounting for model mixing (Haiku vs Opus).

Agent Behavior Equation

The Formula:

Agent Behavior = Model Capability × Profile Configuration

Same model, different profiles = Different specialists

// Claude Opus 4 (fixed capability)
model = "claude-opus-4"

// Different profiles → Different behaviors
network_specialist = Agent(model, profile="network_v3.md")
config_specialist = Agent(model, profile="config_v2.md")

// network_specialist.diagnose(bgp_failure) → 94% accuracy
// config_specialist.diagnose(nat_failure) → 96% accuracy

// Same capability, different behavior!

Key insight: Change behavior without retraining - just edit profile

Speaker Notes

The Agent Behavior Equation is the fundamental formula: Agent Behavior = Model Capability × Profile Configuration. Model Capability is the raw intelligence (reasoning ability, knowledge breadth, instruction-following) - FIXED, you can't change Claude Opus 4's capabilities. Profile Configuration is the identity, expertise, procedures, constraints - CONFIGURABLE, you can change it by editing the profile markdown file. Agent Behavior is the actual outputs and decisions - EMERGENT from capability × configuration. The power: You can create different specialists from the SAME model just by changing the profile. Claude Opus + network_profile = 94% accuracy on network failures. Claude Opus + config_profile = 96% accuracy on config failures. Same model, same input, different behaviors based on profile! Key insight: A weaker model (Haiku) with an excellent profile can outperform a stronger model (Opus) with a poor profile. Haiku + excellent_profile (82%) beats Opus + poor_profile (68%). Investing in profile quality gives more ROI than upgrading the model.

Capability-versus-Behavior Separation

Capabilities (Fixed):

  • Claude Opus 4: 200K context, graduate-level reasoning
  • Claude Haiku 4: 8K context, undergraduate-level reasoning

Behavior (Configurable):

  • Network specialist: Diagnose BGP issues, cite routing tables
  • Config specialist: Diagnose NAT issues, cite policy rules

Same capability → Multiple behaviors via profiles

Opus + network_profile → Network specialist (94% accuracy)
Opus + config_profile  → Config specialist (96% accuracy)

Haiku + network_profile → Network specialist (82% accuracy)
Haiku + config_profile  → Config specialist (84% accuracy)

Strategy: Use cheap Haiku where capability suffices, expensive Opus where needed

Speaker Notes

Capability-versus-behavior separation is about understanding that model capabilities are FIXED (what the model CAN do) but behavior is CONFIGURABLE (what the model ACTUALLY does in your system). Claude Opus 4 capabilities: 200K context window, graduate-level reasoning, excellent instruction-following, $15/M input tokens. Claude Haiku 4: 8K context, undergraduate-level reasoning, good instruction-following, $2.50/M input tokens (7x cheaper). You can't make Haiku reason like Opus, but you CAN configure both to be network specialists. The strategy: Model mixing based on the behavior equation. Specialists (narrow behavior) require medium capability → Use Haiku (sufficient, 7x cheaper). General diagnostician (broad behavior) requires high capability → Use Opus (expensive but necessary). Result: 91% accuracy for $0.0155 average cost by using Haiku for 95% of cases (specialists) and Opus for 5% (general fallback).

Deterministic Profile Selection

Why deterministic?

  • ✅ Predictable (same input → same specialist)
  • ✅ Debuggable (explain selection logic)
  • ✅ Improvable (add rules based on errors)
  • ❌ ML-based routing: Black box, needs training data
  • ❌ LLM-based routing: Non-deterministic, extra cost

Rule-based selection:

if "bgp" in test_name or "route not found" in logs:
    → network_diagnostician
elif "nat" in test_name or "policy lookup failed" in logs:
    → config_diagnostician
elif "timeout" in test_name or "timed out" in logs:
    → timing_diagnostician
else:
    → general_diagnostician (fallback)

Accuracy: 92% (correct specialist first try)

Speaker Notes

Deterministic profile selection is the routing layer that decides which specialist to use. The key design choice: Use simple rules, not ML or LLM. Why deterministic? PREDICTABLE - same failure always routes to same specialist (no randomness). DEBUGGABLE - can explain why specialist was selected ("Selected network_diagnostician because test_name contains bgp"). IMPROVABLE - track selection accuracy, analyze errors, add better rules over time. Why NOT ML-based routing? Needs training data (labeled failures with ground truth specialist), black box (can't explain selection), can drift over time. Why NOT LLM-based routing? Non-deterministic (temperature >0 for reasoning), extra API call (costs money, adds latency), can be wrong. Rule-based wins: Fast (0.05s), free (no API), deterministic, debuggable, improvable. Selection accuracy 92% means 92% of failures routed to correct specialist first try, 8% require cascading but eventually get correct specialist (99.2% effective routing).

Multi-Specialist Cascade Flow

Reason: "bgp" in test_name Network->>Network: Analyze... Network->>Selector: OUT_OF_SCOPE
Recommended: config_diagnostician Selector->>Config: Same failure Config->>Config: Analyze... Config->>Selector: IN_SCOPE
Root cause: Missing policy for BGP peer Note over Selector,Config: 96% confidence, diagnosis complete

Cascade rate: 8% (specialist returns OUT_OF_SCOPE)

Fallback rate: 1% (cascade to general)

Speaker Notes

The multi-specialist cascade flow handles routing errors gracefully. Scenario: Test name says "bgp" but failure is actually a config issue. Step 1: Selector picks network specialist (rule: "bgp" in test_name). Step 2: Network specialist analyzes, realizes it's a policy issue (not network connectivity), returns OUT_OF_SCOPE with recommended_specialist=config_diagnostician. Step 3: System cascades to config specialist. Step 4: Config specialist diagnoses successfully (96% confidence, missing policy rule). Why this works: Specialists have explicit scope (network ONLY handles network.routing/vpn/tunnel), OUT_OF_SCOPE includes recommendation, max cascade depth prevents loops. Cascade statistics: 8% overall cascade rate, network to config (36 cases/hour, 8% of network selections), config to network (23 cases/hour, 6.5%), any to general (10 cases/hour, 1%). Cascade is not a bug, it's a feature - allows simple selection rules + specialist scope discipline to achieve 99.2% correct routing.

Summary

5 Core Concepts:

  1. Agent Profiles: Reusable markdown definitions (identity + expertise + procedures + constraints)
  2. Profile-vs-Prompt Separation: Profile = WHO (cached), Prompt = WHAT (fresh)
  3. Behavior Equation: Behavior = Capability × Profile (change profile to change behavior)
  4. Capability-vs-Behavior: Capability fixed, behavior configurable (enables model mixing)
  5. Deterministic Selection: Rule-based routing (predictable, debuggable, improvable)
