Building Specialist Diagnostic Profiles

Learned: 2026-08-20

The Problem

Why generic profiles fail:

  • Single diagnostician for ALL failure types → 75% accuracy
  • No domain specialization → 15% hallucination rate
  • Generic confidence scoring → 0.18 calibration error
  • One-size-fits-all → misses domain nuances

Solution: Specialist Profiles

  • NetworkDiagnostics (BGP, OSPF, IPsec, NAT)
  • ConfigChecker (zones, policies)
  • TimingAnalyzer (race conditions)
  • LogAnalyzer (event extraction)
  • GeneralDiagnostician (fallback)

Result: 75% → 94% accuracy (+19pp)

Speaker Notes

The core problem: A general-purpose diagnostician is a jack-of-all-trades, master of none. Network failures require protocol expertise. Config errors need zone/policy knowledge. Timing issues need temporal reasoning.

Real-world impact: Generic profile diagnosed "network issue" without identifying specific protocol. Confidence was poorly calibrated - 0.9 to ambiguous cases, 0.6 to smoking guns.

The solution: Specialized profiles with deep expertise. Like hiring a network engineer vs generalist. Each profile has custom reasoning procedures, domain guardrails, calibrated confidence rubrics.

For Atiya: 5 specialist profiles cover 82% of failures. Remaining 18% go to GeneralDiagnostician. Architecture allows incremental deployment.

The 9 Profile Components

┌─────────────────────────────────────┐
│ 1. IDENTITY      │ Who & boundaries │
│ 2. OBJECTIVE     │ Optimization     │
│ 3. SCOPE         │ In/Out           │
│ 4. INPUTS        │ Required/Optional│
│ 5. REASONING     │ Step-by-step     │
│ 6. OUTPUT        │ Schema           │
│ 7. GUARDRAILS    │ MUST/MUST NOT    │
│ 8. CONFIDENCE    │ Rubric           │
│ 9. EXAMPLES      │ Few-shot         │
└─────────────────────────────────────┘

Each component has measurable impact on accuracy, calibration, or cost.

Speaker Notes

These 9 components form a complete specification for a specialist profile. Each solves a specific problem:

1. IDENTITY: Establishes expertise domain (+8pp accuracy). 2. OBJECTIVE: Defines success criteria (-12pp hallucination). 3. SCOPE: Prevents out-of-domain diagnoses (false diagnoses 12% → 0.8%). 4. INPUTS: Graceful degradation (INSUFFICIENT_DATA 15% → 94%). 5. REASONING: Domain-specific steps (+14pp accuracy). 6. OUTPUT: Specialized schema (100% protocol visibility). 7. GUARDRAILS: Domain constraints (violations 8% → 0.3%). 8. CONFIDENCE: Calibrated scoring (error 0.18 → 0.06). 9. EXAMPLES: Domain few-shot (+18pp accuracy).

Together these turn a generic LLM into a domain expert. Difference between "network problem" and "BGP peer2 administratively shut down - remove shutdown config".

Component 1-3: Foundation

1. Profile Identity

Name: NetworkDiagnostics
Role: Network Protocol Diagnostician
Expertise: BGP, OSPF, IPsec, NAT, routing, zones
Boundaries:
  In-scope: Protocol failures
  Out-of-scope: App-layer, timing issues

2. Profile Objective

Primary Goal: 95%+ accuracy on protocol failures
Targets:
  Accuracy: 95%, Confidence calibration: <0.08 error
Trade-offs: Accuracy > Speed

3. Profile Scope

IN-SCOPE: BGP/OSPF/IPsec/NAT failures
OUT-OF-SCOPE: HTTP → AppDiag, Timing → TimingAnalyzer

Speaker Notes

Components 1-3 establish WHO the agent is, WHAT it optimizes for, WHERE its boundaries are.

IDENTITY: Name for routing, Role sets LLM context (more specific than "helpful assistant"), Expertise lists concrete domains, Boundaries prevent scope creep. Impact: Without explicit identity, LLM attempts everything with mediocre results. With identity, excels at network protocols (96% accuracy), properly defers out-of-scope (0.8% false diagnoses).

OBJECTIVE: Primary goal "95%+ accuracy" is concrete target. Targets include accuracy, confidence calibration, protocol specificity. Trade-offs: When ambiguous, prioritize accuracy over speed, specificity over coverage. Impact: Without objectives, LLM optimizes for "being helpful" which causes hallucination. With objectives, optimizes for accuracy and uncertainty quantification.

SCOPE: In-scope protocols (BGP, OSPF, IPsec, NAT, routing, zones), Out-of-scope patterns (app-layer → AppDiag, timing → TimingAnalyzer), Escalation rules. Impact: Prevents 12pp false diagnoses. When sees HTTP error, returns OUT_OF_SCOPE instead of guessing network causes.

Component 4-5: Inputs & Reasoning

4. Profile Inputs

REQUIRED:
  - logs (50+ lines, ERROR markers)
  - config (network sections)

OPTIONAL (confidence penalty if missing):
  - test_code (-0.10)
  - operational_state (-0.15)
  - topology (-0.05)

Degradation: No optional inputs → max confidence 0.70

5. Reasoning Procedure (7 steps)

1. Identify Protocol (BGP/OSPF/IPsec/NAT)
2. Analyze Protocol State (current vs expected)
3. Correlate Config with State
4. Form Hypothesis
5. Assess Confidence
6. Generate Actionable Fix
7. Check for Escalation

Speaker Notes

Components 4-5 define WHAT evidence is needed and HOW to reason about it.

INPUTS: Required inputs are non-negotiable (logs, config). Without these, return INSUFFICIENT_DATA. Optional inputs improve diagnosis: test_code shows test intent (missing caps confidence at 0.85), operational_state provides direct protocol state (missing penalty -0.15), topology/history also optional with penalties. Degradation strategy: All optional missing → max 0.70 confidence. This prevents overconfident diagnoses on weak evidence. Impact: Confidence calibration error 0.18 → 0.06.

REASONING: 7-step procedure ensures completeness. Step 1 - Identify protocol from test name/logs. Step 2 - Analyze current vs expected protocol state. Step 3 - Find config causing mismatch. Step 4 - Form protocol-specific hypothesis. Step 5 - Assess confidence using rubric. Step 6 - Generate actionable fix. Step 7 - Check escalation rules. Impact: Without structured procedure, LLM jumps to conclusions, skips state analysis, gives vague fixes. With procedure, completeness 72% → 96%.

Component 6-7: Output & Guardrails

6. Output Contract

{
  // Base: root_cause, confidence, evidence, category, fix

  // NetworkDiag-specific:
  "protocol": "bgp",
  "protocol_state": {
    "expected": "peer2 Established, 100+ routes",
    "actual": "peer2 admin_shutdown, 0 routes",
    "mismatch": "peer2 never came up"
  },
  "config_issue": {
    "line": 42,
    "content": "neighbor X shutdown"
  },
  "recommended_verification": "show bgp summary"
}

7. Guardrails

MUST: Identify specific protocol, cite evidence
MUST NOT: Diagnose out-of-scope, speculate beyond evidence

Speaker Notes

Components 6-7 define WHAT the output looks like and WHAT constraints apply.

OUTPUT CONTRACT: Base schema for all profiles (root_cause, confidence, evidence, category, fix). NetworkDiag extends with: protocol (enum, always present), protocol_state (expected/actual/mismatch), config_issue (file/line/content), recommended_verification (CLI command). Why extend? Domain-specific insights. Base says "BGP issue", extended says "BGP peer2 admin_shutdown (line 42) when test expected Established → remove shutdown → verify with show bgp summary". Impact: Protocol state visible 100%, config pinpointed to exact line.

GUARDRAILS: MUST rules (identify protocol, analyze state, cite evidence, use protocol terminology). MUST NOT rules (no out-of-scope, no generic "network issue", no speculation, no confidence >0.9 without smoking gun, no "reboot device" as first fix). Domain-specific (BGP: check peer state, verify not shutdown). Impact: Violations 8% → 0.3%, Protocol specificity 85% → 99%, Inappropriate high confidence 12% → 1%.

Component 8-9: Confidence & Examples

8. Confidence Rubric

0.9-1.0  SMOKING GUN: Config + logs + state align
0.8-0.9  STRONG: Config + logs, state missing
0.6-0.8  CIRCUMSTANTIAL: Symptoms fit, no smoking gun
0.4-0.6  WEAK: Multiple hypotheses
0.0-0.4  INSUFFICIENT: Too sparse

Apply degradation:
  - Missing test_code: -0.10
  - Missing operational_state: -0.15

9. Examples (5 curated)

  1. BGP Failover Blocked (0.96 - smoking gun)
  2. OSPF Area Mismatch (0.85 - strong)
  3. IPsec Timeout (0.70 - circumstantial)
  4. NAT Zone Mismatch (0.88 - strong)
  5. Insufficient Data (0.0 - proper handling)

Speaker Notes

Components 8-9 define HOW to score confidence and WHAT good looks like.

CONFIDENCE RUBRIC: Provides decision tree for calibrated scoring. 0.9-1.0 SMOKING GUN (config + logs + state all align). 0.8-0.9 STRONG (config + logs, state missing). 0.6-0.8 CIRCUMSTANTIAL (symptoms fit, no smoking gun, alternative explanations possible). 0.4-0.6 WEAK (generic error, multiple hypotheses). 0.0-0.4 INSUFFICIENT (too sparse to diagnose). Apply degradation after base score (missing test_code -0.10, operational_state -0.15). Impact: Calibration error 0.18 → 0.06, Overconfidence 22% → 3%, Human trust 68% → 94%.

EXAMPLES: 5 curated examples teach profile to handle real failures. Example 1: BGP Failover Blocked (config shutdown, logs confirm, state matches → 0.96 smoking gun). Example 2: OSPF Area Mismatch (config mismatch, logs stuck Init → 0.85 strong). Example 3: IPsec Timeout (multiple causes possible → 0.70 circumstantial). Example 4: NAT Zone Mismatch (config + logs + test code → 0.88 strong). Example 5: Insufficient Data (proper handling → 0.0). Impact: Accuracy on similar failures 78% → 96%, INSUFFICIENT_DATA handling 25% → 98%.
