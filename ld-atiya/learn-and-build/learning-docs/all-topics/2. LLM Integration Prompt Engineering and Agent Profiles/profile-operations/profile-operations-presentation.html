The Problem

Why manual profile management fails:

  • Deployment risk: 1 bad deploy/month → $5,000 incident cost
  • Slow iteration: 45 min/deploy (manual) → 1 change/week velocity
  • Downtime: 10 min/deploy → service interruption
  • High costs: $0.105/diagnosis (no caching) → $3,150/month
  • No rollback: 15 min mean time to rollback (manual)
  • No testing: Deploy to 100% immediately → high risk

Solution: Profile Operations

  • Safe deployment: A/B testing catches regressions → 0 incidents
  • Fast iteration: 3 min/deploy (automated) → 5 changes/week
  • Zero downtime: Hot-reload → 99.99% uptime
  • Cost optimized: $0.087/diagnosis (caching) → $1,910/month
  • Instant rollback: 30 sec automated → 30x faster
  • Gradual rollout: 10% canary → 50% → 100% → low risk

Speaker Notes

Real-world context: When you hardcode prompts in Python, every behavior change requires a code deploy. This is slow (compile, test, deploy), risky (no gradual rollout), and prevents non-engineers from improving prompts.

The cost impact is massive. Without prompt caching, you pay full price for system prompts on every request. At 1000 diagnoses/day, that's $3,150/month. With caching and profile operations, you pay $1,910/month - a savings of $1,240/month.

Deployment safety is critical. If you deploy a bad prompt to 100% of traffic, you diagnose 1000 failures incorrectly before you catch the issue. With A/B testing, you deploy to 10% canary, monitor metrics for 2 hours, and catch regressions before they affect 90% of users.

For Atiya specifically, this is Phase 2 work (after prompt engineering fundamentals). Without profile operations, we can't iterate safely at production scale. This is the difference between "works in dev" and "works in prod at 1000 diagnoses/day".

Topic 1: Profiles as Policies

Pattern: Declarative Profile Definition

Profiles are markdown files, not Python code:

---
profile_id: network_diagnostician
version: 2
status: production
traffic_allocation: 0.90
cost_budget: 0.50
accuracy_target: 0.90
---

# IDENTITY
You are Atiya, an expert PARTS test failure diagnostician.

# OBJECTIVE
Identify root cause with 90%+ accuracy.

# CONSTRAINTS
- ONLY cite evidence present in logs/configs
- If insufficient, return "INSUFFICIENT_DATA"

Why: Decouples behavior from code → non-engineers can update prompts

Speaker Notes

Profiles as policies means treating prompts as declarative configuration, not imperative code. The anti-pattern is hardcoded prompts in Python (every behavior change requires code deploy, no A/B testing, no version history, no non-engineer contributions).

The correct pattern: Profiles are markdown files in profiles/ directory with YAML frontmatter defining metadata (profile_id, version, status, traffic_allocation, cost_budget, accuracy_target) and body defining prompt content (IDENTITY, OBJECTIVE, EXPERTISE, REASONING PROCEDURE, CONSTRAINTS, OUTPUT FORMAT, EXAMPLES).

Benefits: 1) Declarative - entire profile is data, can be versioned in git. 2) Testable - CI can run test suite against profile before deploy. 3) Reviewable - non-engineers can review and approve. 4) Deployable - no code changes needed, just update file. 5) Versionable - can diff v1 vs v2. 6) Rollbackable - revert to previous version via git.

For Atiya: QA engineers can add new few-shot examples when they find misdiagnoses. Product can adjust accuracy_target and cost_budget. Engineering can improve reasoning procedures. All via simple markdown edits, no code deploy required. Impact: Iteration velocity 1 change/week → 5 changes/week (non-engineers can contribute).

- Added 3 new BGP failure examples

"

# Push and create PR

# CI runs: lint, validate, test, measure metrics

# Merge triggers deploy to 10% canary
# Monitor metrics: accuracy, cost, latency
# Auto-promote to 100% if metrics pass

Speaker Notes

Version-controlled profiles use git to track profile changes over time, enabling diff, blame, history, and rollback. Why git? 1) History - see all changes to profile over time. 2) Diff - understand exact changes between versions. 3) Blame - see who changed what and why. 4) Rollback - revert to previous version if needed.

Git workflow: 1) Create feature branch. 2) Edit profile (copy v2 as baseline, make changes). 3) Commit with descriptive message. 4) Push and create PR. 5) CI validation runs automated tests. 6) Review (engineering, QA, product). 7) Merge to main triggers deploy to staging (10% canary). 8) Monitor 2 hours. 9) Promote if metrics pass (10% → 50% → 100%). 10) Rollback if metrics fail.

A/B Testing with Git Tags: Tag production versions for easy rollback (git tag v2-production, git tag v3-canary-10pct). List all production versions, rollback to previous tag.

CI/CD Integration: GitHub Actions workflow runs on every PR to profiles/ (validate syntax, run test suite, measure metrics, compare to baseline, post results to PR). On merge to main: deploy to staging, monitor, auto-promote or auto-rollback.

For Atiya: Git provides audit trail of all profile changes. If accuracy regresses, we can git blame to see who changed what, git diff to see exact changes, and git checkout to rollback. Impact: Mean time to rollback 15 min → 30 sec (30x faster).

Topic 3: Profile Loading

Pattern: Lazy Loading + Cache + Hot-Reload

class ProfileLoader:
    def __init__(self, profiles_dir="profiles", cache_ttl=300):
        self._cache = {}  # In-memory cache
        self._routing = {}  # A/B test routing

    def load_profile(self, profile_id: str, version: int) -> Profile:
        cache_key = f"{profile_id}_v{version}"

        # Check cache
        if cache_key in self._cache:
            if self._is_cache_fresh(cache_key):
                return self._cache[cache_key]  # Cache hit

        # Load from disk
        profile = self._load_from_disk(profile_id, version)
        self._cache[cache_key] = profile
        return profile

    def get_profile_for_request(self, profile_id: str,
                                 request_id: str) -> Profile:
        # A/B routing: 90% v2, 10% v3
        version = self._route_request(profile_id, request_id)
        return self.load_profile(profile_id, version)

    def hot_reload(self, profile_id: str, version: int):
        # Force reload from disk (zero downtime)
        cache_key = f"{profile_id}_v{version}"
        del self._cache[cache_key]
        return self._load_from_disk(profile_id, version)

Speaker Notes

Profile loading solves three problems: 1) How to load profiles at runtime, 2) How to cache profiles to avoid repeated disk reads, 3) How to update profiles without restarting the service.

The key patterns: 1) Lazy Loading - load profiles on first use, not at startup (startup 5s → 0.1s, 50x faster). 2) In-Memory Cache - keep loaded profiles in memory (50ms disk read → 0.001ms memory lookup, 50,000x faster). 3) Hash-Based Cache Validation - detect file changes (automatic cache invalidation). 4) Hot-Reload - update profile without service restart (10 min downtime → 0 sec). 5) A/B Routing - different users get different profile versions (gradual rollout).

Profile structure: profile_id, version, content, system_prompt, loaded_at, file_hash. Loading flow: Request → route to version based on A/B config → check cache → if hit and fresh and hash matches, return cached → if miss or stale or hash mismatch, load from disk → parse markdown, extract YAML frontmatter, validate schema → cache in memory → return profile.

A/B Routing logic: Consistent hashing based on request_id. Same request always gets same version. Example: routing = {2: 0.9, 3: 0.1}. If hash(request_id) < 0.9 → v2, else → v3.

Hot-reload: Watch profiles/ directory for file changes. When profile file changes: delete from cache, reload from disk, new requests get updated profile, zero downtime.

For Atiya: ProfileLoader enables A/B testing (90% stable v2, 10% canary v3) and hot-reload (update prompts without downtime). Performance: Cold load 50ms, warm load 0.001ms (50,000x faster). Impact: Deployment time 45 min → 3 min (14x faster).

Topic 4: Profile Caching

Pattern: Claude Prompt Caching (90% cost reduction)

response = client.messages.create(
    model="claude-opus-4",
    system=[
        {
            "type": "text",
            "text": profile.system_prompt,  # 1500 tokens
            "cache_control": {"type": "ephemeral"}  # ← CACHE THIS
        }
    ],
    messages=[{"role": "user", "content": logs}]  # 500 tokens
)

# Request 1 (cache creation):
# Input: 2000 tokens × $15/M = $0.030
# Output: 1000 tokens × $75/M = $0.075
# Total: $0.105

# Request 2-N (cache hit, within 5 min):
# Cached: 1500 tokens × $1.50/M = $0.0023 (90% off)
# Fresh: 500 tokens × $15/M = $0.0075
# Output: 1000 tokens × $75/M = $0.075
# Total: $0.0848 (19% savings)

At 90% cache hit rate: $0.0868 avg cost (17% savings)

Speaker Notes

Profile caching is the single most impactful cost optimization you can do. The problem: Without caching, you pay full price for profile content on every request. At 1000 diagnoses/day: $105/day = $2,310/month.

The solution: Claude's prompt caching. How it works: 1) Mark profile content as cacheable using cache_control: ephemeral. 2) First request creates cache - Claude computes SHA256 hash, stores in cache with 5-minute TTL, charges full price. 3) Subsequent requests (within 5 min) read from cache - Claude computes hash, finds match in cache, charges 90% less.

Cost breakdown: Request 1 (cache creation) $0.105. Request 2 (cache hit) $0.0848, savings $0.0202 (19%). At 90% cache hit rate: Cache misses (10%) 100 × $0.105 = $10.50, Cache hits (90%) 900 × $0.0848 = $76.32, Total daily $86.82, Total monthly $1,910, Savings $400/month (17% reduction).

How to maximize cache hit rate: 1) Batch requests within 5-minute windows (at 1000/day over 8 hours, ~10 diagnoses share one cache, 90% hit rate). 2) Keep profile content stable (don't change frequently, group related changes, deploy during low-traffic). 3) Warm cache after deployment (make dummy request, prevents first user hitting cache miss).

Cache invalidation: Events that invalidate cache: 5-minute TTL expires, profile content changes (hash mismatch), profile version switch (A/B routing change), manual cache clear (debugging).

For Atiya: Caching saves $400/month at 1000 diagnoses/day. As we scale to 10,000/day, savings scale to $4,000/month. This is ON TOP OF savings from system/user separation. Combined savings: $63/day = $1,890/month. ROI: Caching is free (no engineering cost), just add cache_control. Instant $400/month savings.

Speaker Notes

This architecture diagram shows the two cache layers: 1) Application-level cache (in-memory, ProfileLoader), 2) Claude API cache (server-side, prompt caching).

Request 1 (Cache MISS): Request comes in (cache is cold). ProfileLoader checks in-memory cache → MISS. Load profile from disk (50ms, 1500 tokens). Call Claude API with cache_control: ephemeral. Claude computes SHA256 hash of profile content. No matching hash in cache → CREATE CACHE. Store profile in Claude's cache with 5-minute TTL. Process request normally. Return response with usage (cache_creation_input_tokens: 1500). Cost: $0.105. ProfileLoader caches profile in memory.

Request 2-10 (Cache HIT, within 5 minutes): Request comes in. ProfileLoader checks in-memory cache → HIT (0.001ms lookup). Return cached profile (no disk read). Call Claude API with same profile content. Claude computes hash. Finds matching hash in cache (TTL not expired). Read 1500 tokens from cache (cheap), process 500 fresh tokens (full price). Return response with usage (cache_read_input_tokens: 1500). Cost: $0.0848, savings $0.0202 (19%).

Cache hit rate with steady traffic: Assuming 1000 diagnoses/day over 8-hour workday: 125/hour, 2.1/minute, ~10 diagnoses per 5-minute cache window. First diagnosis creates cache (cache miss), next 9 hit cache. Cache hit rate: 9/10 = 90%. Average cost with 90% hit rate: $0.0868. Savings vs no caching: $0.0182 per diagnosis (17% off). At scale: $18.20/day = $400/month saved.

Cache monitoring: Track cache hit rate with metrics. Alert if hit rate drops below 70% (indicates cache thrashing or profile changes too frequently).

For Atiya: Two-layer caching (app-level + Claude-level) provides: 1) Fast profile loading (0.001ms vs 50ms), 2) Cost savings (17% reduction), 3) Resilience (app cache survives Claude cache expiration). Impact: $400/month savings, zero engineering cost to enable.

Topic 5: Profile Restart Behavior

Pattern: Stateless Design (each diagnosis independent)

class StatelessDiagnosticEngine:
    def diagnose(self, test_name: str, logs: str,
                 prior_diagnosis: Dict = None) -> Dict:
        # Each call is independent (no shared state)
        user_prompt = f"Diagnose {test_name}: {logs}"

        # Optional: Inject prior diagnosis as context
        if prior_diagnosis:
            user_prompt = f"""
            Prior diagnosis: {prior_diagnosis['root_cause']}
            Fix applied: {prior_diagnosis['recommended_fix']}
            Test re-run, still failed.

            {user_prompt}
            """

        # Single-turn request (no conversation history)
        response = client.messages.create(
            model="claude-opus-4",
            system=profile.system_prompt,
            messages=[{"role": "user", "content": user_prompt}]
        )

        return json.loads(response.content[0].text)

Benefits: Predictable, debuggable, parallelizable, cost-effective

Speaker Notes

Profile restart behavior defines how profiles handle state and context across multiple calls. Design decision: STATELESS (each diagnosis independent).

Why stateless? 1) Predictability - same input always produces same output, no hidden state. 2) Debuggability - each diagnosis is self-contained, can replay in isolation. 3) Parallelizability - can run 100 diagnoses concurrently, no shared state, no race conditions. 4) Simplicity - no state management complexity, no context window limits, no memory leaks. 5) Cost - no conversation history to send (stateful requires sending entire conversation on each request, cost grows linearly with conversation length, stateless has fixed cost per request).

Anti-pattern (stateful): Maintain conversation_history list that grows unbounded. Send entire history to Claude on each request. Problems: History grows unbounded (memory leak), cost increases with each diagnosis, can't parallelize (shared state), can't replay single diagnosis, unclear when to reset history.

Cost comparison: Stateless - Diagnosis 1-3 each cost $0.030 (2K input), total $0.090. Stateful - Diagnosis 1 $0.030 (2K input), Diagnosis 2 $0.060 (4K input includes history), Diagnosis 3 $0.090 (6K input includes history), total $0.180 (2x more expensive).

Correct pattern (stateless with optional context): Each diagnosis is independent, but user can provide prior diagnosis as context. Inject prior diagnosis as explicit context (not automatic). User controls context (not automatic). Cost is predictable (no unbounded growth).

When to use stateful: Don't use for Atiya (each test failure is independent, no benefit from remembering prior diagnoses, cost increases). Do use for chatbots (user asks follow-up questions, context from prior messages is necessary, conversation is short <20 turns).

For Atiya: Stateless design is correct. Each test failure is diagnosed independently. If engineer wants to provide prior diagnosis as context (e.g., "test failed again after fix"), they can pass it explicitly. Impact: Predictable cost, no memory leaks, can parallelize, easy to debug.
