Slide 1: The Problem

Why do naive prompts fail?

  • Random outputs: 45% accuracy ❌
  • Hallucinations: 30% of responses ❌
  • Parsing failures: 25% (malformed JSON) ❌
  • Cost: $0.85/diagnosis (retries) ❌

Solution: Systematic prompt engineering

  • 90%+ accuracy ✓
  • <5% hallucination rate ✓
  • <1% parsing failures ✓
  • $0.42/diagnosis (50% cost reduction) ✓

Speaker Notes

Real-world context: When we started building Atiya, we threw raw logs at Claude with prompts like "diagnose this failure." Results were unusable: 45% accuracy means every other diagnosis was wrong, 30% hallucination rate means Claude invented plausible-sounding explanations with no evidence, 25% parsing failures means we couldn't even extract structured data.

The cost impact is hidden: When you get a wrong diagnosis, you retry. When you get malformed JSON, you retry. Each retry costs money. At scale (1000 failures/day), this adds up fast.

Prompt engineering is NOT about "being nice to the AI" - it's about deterministic control of a probabilistic system. Every pattern we'll cover is backed by metrics showing measurable improvement.

For Atiya specifically, this is the foundation. Without reliable prompts, nothing else works - not RAG, not multi-agent, not cost optimization. This is week 1 work.

Slide 2: Architecture Overview

graph TD A[Diagnosis Request
test_bgp_failover failed] --> B[Prompt Engineering Layer] B --> C[System Prompt
WHO/WHAT/HOW] B --> D[User Prompt
TASK/EVIDENCE] B --> E[Per-Step Templates
Multi-agent flow] C --> F[Claude API] D --> F E --> F F --> G[Structured Output
root_cause + confidence + evidence] style A fill:#e1f5fe style B fill:#fff3e0 style F fill:#f3e5f5 style G fill:#c8e6c9

Key: Prompts are code - structured, versioned, testable

Speaker Notes

This architecture diagram shows the three layers of prompt engineering: 1) System Prompt (WHO/WHAT/HOW) - like programming the agent, defines identity, expertise, reasoning procedure, constraints, and output format. Rarely changes, versioned like code. 2) User Prompt (TASK/EVIDENCE) - like calling a function, provides the specific task and all evidence needed. Changes every request. 3) Per-Step Templates - for multi-agent workflows, different prompts for different steps (log parsing, config analysis, synthesis).

The mental model: System prompt = programming, User prompt = function call.

Why this matters for Atiya: System prompts can be cached (5min TTL) = cost savings. User prompts are evidence-rich = better accuracy. Templates enable multi-agent workflows = specialized expertise.

The key insight: "Prompts are code" means they deserve the same rigor as your Python code - version control, testing, code review, monitoring.

Slide 3: LLM API Integration

Parameters that matter:

Parameter Purpose Atiya Value Impact
model Which Claude opus-4 Accuracy
temperature Randomness 0.0 Determinism
max_tokens Output limit 4096 Cost vs completeness
system Agent profile Full profile Behavior
stop_sequences Early exit ["</diagnosis>"] Cost

Cost (Claude Opus 4):

  • Input: $15/million tokens → 2K tokens = $0.030
  • Output: $75/million tokens → 1K tokens = $0.075
  • Total: $0.105/diagnosis

Speaker Notes

model: We use Opus 4 (most capable) for Atiya because diagnosis requires complex reasoning. The accuracy delta (85% vs 92%) costs more in wasted human review time than the model price difference.

temperature: 0.0 = deterministic (same input always gives same output). For production diagnostics, you MUST use 0.0. If you use 0.7 (creative), you'll get different diagnoses for the same failure, which destroys user trust.

max_tokens: 4096 is enough for a complete diagnosis. Too low (1024) cuts off mid-sentence. Too high (8192) wastes money.

system: Your agent profile. Never put this in the user prompt - it prevents caching and costs 10x more.

stop_sequences: If you have structured output like XML, tell Claude to stop at </diagnosis>. Saves ~200 tokens per call.

Cost breakdown for Atiya at 1000 diagnoses/day: Base cost $105/day = $3,150/month. With optimizations (caching, stop sequences): $65/day = $1,950/month.

Slide 4: System Prompt - The 7 Components

┌───────────────────────────────┐
│  1. IDENTITY                  │  Who the agent is
│  2. OBJECTIVE                 │  What it optimizes for
│  3. EXPERTISE/CONTEXT         │  Domain knowledge
│  4. REASONING PROCEDURE       │  Step-by-step thinking
│  5. CONSTRAINTS & GUARDRAILS  │  MUST/MUST NOT rules
│  6. OUTPUT FORMAT             │  Exact structure
│  7. EXAMPLES (Few-shot)       │  3-5 input→output pairs
└───────────────────────────────┘

Example:

# IDENTITY
You are Atiya, an expert PARTS test failure diagnostician.

# OBJECTIVE  
Identify root cause with 90%+ accuracy by analyzing logs/configs.

Speaker Notes

The system prompt is the most important part of prompt engineering. This is where you "program" the agent's behavior. Each component serves a specific purpose with measurable impact:

1. IDENTITY: "You are Atiya" is better than "You are a helpful assistant" - primes Claude with domain context. Impact: +8pp accuracy.

2. OBJECTIVE: "90%+ accuracy by analyzing logs/configs" tells Claude to be precise, not creative. Impact: -12pp hallucinations.

3. EXPERTISE: Lists what the agent knows (PARTS framework, PAN-OS networking, common failures, log formats). Impact: +15pp accuracy on domain questions.

4. REASONING PROCEDURE: Step-by-step instructions. Critical for complex reasoning. Without it, Claude jumps to conclusions. Impact: +18pp accuracy, -22pp hallucination.

5. CONSTRAINTS: MUST/MUST NOT rules. "ONLY cite evidence present" prevents hallucination. Impact: -25pp hallucination rate.

6. OUTPUT FORMAT: Exact JSON schema with types, validation rules, example. Impact: 75% → 99.8% valid JSON responses.

7. EXAMPLES: 3-5 input→output pairs showing edge cases. Impact: +27pp accuracy on edge cases.

Total impact: Naive prompt (45% accuracy) → 7-component system prompt (90% accuracy). For Atiya, we version this as prompts/atiya_diagnostician_v2.md in git.

Slide 5: User Prompt Design

Pattern: Task + Evidence + Context

❌ Bad (vague):

Diagnose test_bgp_failover failure

✅ Good (precise):

Diagnose why test_bgp_failover failed on TB-SASE-01 at 2026-08-20T14:32:18Z.

<test_code>
def test_bgp_failover(topology, dut):
    """Verify BGP fails over to secondary peer within 60s"""
    topology.peer1.admin_down()
    time.sleep(60)
    assert dut.get_bgp_routes()['active_peer'] == 'peer2'
</test_code>

<logs>
2026-08-20 14:32:18 ERROR Assertion failed: active_peer = 'peer1'
2026-08-20 14:32:18 INFO BGP routing table shows 0 routes via peer2
</logs>

<device_config>
neighbor peer2 shutdown
</device_config>

Speaker Notes

User prompt design is about giving Claude ALL the evidence it needs to make an accurate diagnosis.

Why the bad example fails: No test code → Claude doesn't know what the test expects. No logs → no failure evidence. No config → can't see misconfigurations. Result: Claude guesses, maybe "network timeout" or "timing issue" - both wrong.

Why the good example works: Test code shows intent (expects active_peer = peer2 after 60s). Logs show actual result (active_peer = peer1, 0 routes via peer2). Config reveals root cause (neighbor peer2 shutdown). Claude can now trace: Test brought down peer1 → expected failover to peer2 → but peer2 was already shut down → assertion failed. Confidence: 0.95 (smoking gun evidence).

We use XML tags to clearly separate different types of evidence. This helps Claude: 1) Parse structured data reliably, 2) Prevent prompt injection, 3) Reference evidence in output.

For Atiya, the evidence collection step (before prompting) is critical: Fetch test source from git, extract relevant log sections (grep -A 50 ERROR), query device configs via PARTS API, assemble into structured user prompt. This is where 60% of the engineering effort goes.

Slide 6: System/User Separation

Mental model:

System Prompt = Programming the agent (runs once)
User Prompt = Calling a function (runs per request)

Why separate?

Aspect System User
Changes Rarely Every request
Caching Yes (5min) No
Cost Free after first Full cost
Length 10K tokens OK Keep concise

ROI for Atiya:

  • 1000 diagnoses/day without caching: $150/day
  • 1000 diagnoses/day with caching: $65/day
  • Savings: $2,550/month

Speaker Notes

This is the single most impactful cost optimization you can do. Claude's API caches system prompts with a 5-minute TTL. If you make a second request within 5 minutes with the SAME system prompt, you pay 90% less for those input tokens.

Example: First call - 1500-token system prompt costs $0.0225. Second call (within 5min) - same system prompt costs $0.0023. 10x cheaper!

Anti-pattern (mixing instructions into user prompt): Every single diagnosis pays for "You are a PARTS diagnostician..." even though it never changes. This costs $0.15 per diagnosis.

Correct pattern: Instructions in system (cached), task in user (fresh). Costs $0.045 per diagnosis after first call.

Atiya ROI calculation: 1000 diagnoses/day during 8-hour workday = 125/hour or ~2/minute. With 5-minute cache TTL, ~10 diagnoses per cache window. 90% of calls get cache hit. Cost: (100 * $0.105) + (900 * $0.045) = $51/day. Without separation: 1000 * $0.15 = $150/day. Savings: $99/day = $2,970/month.

Key insight: System prompt is like compiled code - you write it once, run it many times. User prompt is like runtime data - changes every execution.

Slide 7: Explicit Output Format

Pattern: Format + Schema + Example + Validation

{
  "root_cause": "BGP peer2 was administratively shut down",
  "confidence": 0.95,
  "evidence": [
    "config line 23: neighbor peer2 shutdown",
    "logs line 8: 0 routes via peer2"
  ],
  "failure_category": "config",
  "recommended_fix": "Remove 'neighbor peer2 shutdown'",
  "requires_human_review": false
}

Results:

Metric Vague Explicit
Valid JSON 75% 99.8%
Retries 0.33/req 0.002/req
Cost $0.58 $0.42

Speaker Notes

Explicit output format instructions solve the "parsing hell" problem. When you just say "return JSON", Claude might return: JSON wrapped in markdown (```json\n{...}\n```), JSON with comments, malformed JSON (missing commas), or explanation + JSON. Each breaks json.loads().

Pattern components: 1) Format directive: "Return ONLY valid JSON" prevents wrapping in code blocks. 2) Schema with types: Claude knows exact structure. 3) Concrete example: Shows format in practice. 4) Validation rules: Makes constraints explicit (confidence must be 0.0-1.0, evidence must have >= 1 entry).

Impact: Valid JSON rate 75% → 99.8%. That's 25% failures → 0.2% failures. At 1000 diagnoses/day: 250 parsing failures → 2 parsing failures. Retries saved: 248 * $0.105 = $26/day = $780/month.

For the remaining 0.2%, we have error handling: extract JSON from markdown if present, or ask Claude to fix its own JSON. For Atiya, we also validate the schema after parsing: check all required fields present, check types match, check enums valid, check ranges.

Slide 8: Few-Shot Learning

Teaching through examples (3-5 input→output pairs)

### Example 1: Network timeout
Input: IPsec SA negotiation timeout after 30s
Output: 
{
  "root_cause": "IKE phase 1 timeout - likely crypto mismatch",
  "confidence": 0.75,
  "failure_category": "network"
}

### Example 2: Config error
Input: Policy lookup failed, source zone mismatch
Output:
{
  "root_cause": "NAT policy expects 'trust' but packet from 'untrust'",
  "confidence": 0.98,
  "failure_category": "config"
}

### Example 3: Insufficient data
Input: FAILED Assertion error (no context)
Output:
{
  "root_cause": "INSUFFICIENT_DATA - no diagnostic context",
  "confidence": 0.0
}

Speaker Notes

Few-shot learning is the most powerful technique for teaching complex tasks. LLMs are trained on next-token prediction. When you show examples, Claude's pattern-matching kicks in: "Oh, when I see a timeout, I should say 'likely crypto mismatch' and set confidence to 0.75. When I see INSUFFICIENT_DATA, I should set confidence to 0.0."

When to use: Complex tasks requiring multi-step reasoning, domain-specific patterns, edge cases you want to handle well. Don't use for simple classification or when system prompt is already >8K tokens.

How many examples? 3-5 is optimal. Too few (1-2): Claude doesn't pick up the pattern. Too many (10+): Wastes tokens, diminishing returns. Sweet spot: 3-5 carefully chosen examples covering happy path, ambiguous case, insufficient data case.

For Atiya, we curated examples from real PARTS test failures: 1) Network timeout - shows how to handle ambiguous evidence (could be crypto OR firewall), set confidence to 0.75 when multiple hypotheses fit. 2) Config error - shows how to cite specific config/log lines, high confidence (0.98) when smoking gun present. 3) Insufficient data - shows how to handle "I don't know" case, set confidence to 0.0, return INSUFFICIENT_DATA.

Impact on Atiya: Accuracy on edge cases 62% (zero-shot) → 89% (few-shot). Proper handling of insufficient data 15% → 94%. As we encounter new failure patterns, we add them to examples doc, creating a virtuous cycle.

Slide 9: Explicit Constraints

MUST / MUST NOT rules

## CONSTRAINTS

### Evidence-based reasoning (MUST)
✅ ONLY cite evidence in provided logs/configs
✅ Quote exact lines when referencing evidence

### Handling uncertainty (MUST)
✅ If evidence insufficient → "INSUFFICIENT_DATA"
✅ If confidence < 0.7 → requires_human_review: true

### Prohibited (MUST NOT)
❌ Never speculate beyond evidence
❌ Never recommend "reboot device"
❌ Never suggest "works on my machine"
❌ Never generate fake log lines

Impact: Hallucination rate 28% → 4%

Speaker Notes

Explicit constraints are the guardrails that prevent LLMs from going off the rails. LLMs are trained to be helpful and complete, which creates dangerous behaviors: hallucination (inventing plausible explanations when evidence is weak), generic advice ("check network connectivity" - not actionable), avoiding "I don't know" (guessing rather than admitting insufficient data). Constraints override this training by making the rules absolutely explicit.

Constraint categories: 1) Evidence-based reasoning: "ONLY cite evidence present" prevents hallucination (Claude can't invent log lines). "Quote exact lines" makes evidence verifiable (human can check quotes). Impact: -18pp hallucination, +12pp human trust. 2) Handling uncertainty: "If evidence insufficient, return INSUFFICIENT_DATA" gives explicit escape hatch. "If confidence <0.7, set requires_human_review" escalates uncertain diagnoses. Impact: 15% → 94% proper insufficient-data handling. 3) Prohibited behaviors: Never recommend "reboot device" (last resort, not diagnostic insight). Never suggest "works on my machine" (environmental blame not actionable). Never generate fake log lines (prevents confusion about real vs hypothetical). Impact: -35pp generic/unhelpful recommendations, +15pp actionable fixes.

Results: Hallucination rate 28% → 4%, Generic fixes 45% → 2%, INSUFFICIENT_DATA handling 12% → 96%, Human trust rating 62% → 94%.

We have adversarial test cases specifically designed to violate constraints. For Atiya, constraints are non-negotiable. A hallucinated diagnosis is worse than no diagnosis - it sends engineers down the wrong path and wastes hours.

Slide 10: Per-Step Prompt Templates

Multi-agent workflow with dynamic prompts

sequenceDiagram participant Atiya participant LogParser participant ConfigAnalyzer participant Synthesizer Atiya->>LogParser: Extract events
Template: LOG_PARSER LogParser-->>Atiya: [ERROR events...] Atiya->>ConfigAnalyzer: Find misconfigs
Template: CONFIG_ANALYZER ConfigAnalyzer-->>Atiya: [Zone mismatch...] Atiya->>Synthesizer: Combine findings
Template: SYNTHESIZER Synthesizer-->>Atiya: Final diagnosis

Performance:

  • Single-step: 87% accuracy, 12s, $0.42
  • Multi-step (Haiku→Haiku→Opus): 91% accuracy, 18s, $0.38

Speaker Notes

Per-step templates enable multi-agent workflows where each agent has a specialized task and prompt. Complex tasks benefit from decomposition: Step 1 (Log Parser) - extract structured events from raw logs, Step 2 (Config Analyzer) - find misconfigurations, Step 3 (Synthesizer) - combine findings into final diagnosis.

Benefits: 1) Focused agents - each step has narrow, well-defined task. 2) Debuggability - can inspect intermediate outputs, identify which step failed. 3) Fallback resilience - if step 2 fails, still have step 1 results. 4) Cost control - use cheaper models for simple steps (Steps 1-2: Haiku $0.002 each, Step 3: Opus $0.085).

Why multi-step is more accurate: Log parser can focus just on extraction (simple task), config analyzer can focus just on misconfigs (simple task), synthesizer gets clean structured inputs (easier reasoning), each step has smaller context window (less noise).

Why Haiku→Opus hybrid works: Steps 1-2 are simple (extract, match patterns) - Haiku handles these fine. Step 3 is complex (reasoning, causality) - Opus excels here. Cost: 2*$0.002 + $0.085 = $0.089 vs 3*$0.105 = $0.315.

When to use: Complex tasks (diagnosis, multi-step reasoning), when intermediate outputs are useful (debugging, caching), when you can use cheaper models for some steps. Don't use for simple tasks or when latency is critical (<1s).

Atiya decision: Use multi-step with Haiku→Haiku→Opus for standard diagnoses. For simple failures (obvious error in logs), skip to single-step Haiku diagnosis.

Slide 11: Production Considerations

Performance

  • Latency breakdown: 8.2s avg
  • Prompt construction: 0.1s
  • API call: 0.3s
  • Claude inference: 7.5s
  • Parsing: 0.3s

Cost (1000 diagnoses/day)

  • Without caching: $105/day = $3,150/month
  • With caching: $65/day = $1,950/month
  • Target: <$0.50/diagnosis ✅ $0.085 current

Reliability

  • API timeout (5%) → Retry with backoff → 99.95% success
  • Invalid JSON (0.2%) → Schema validation + fix
  • Rate limiting (60+ concurrent) → Token bucket limiter

Speaker Notes

Production considerations separate a prototype from a real system. Performance - latency breakdown shows where time is spent. Claude inference (7.5s) is what we can't change. Optimization strategies: 1) Reduce prompt size (12s → 8s, 33% faster), 2) Use streaming (time to first token 1.2s, perceived latency), 3) Parallel batch processing (100 failures: 820s sequential → 12s parallel with 60 concurrent).

Cost - Claude Opus 4 pricing: Input $15/M tokens, Output $75/M tokens, Cached input $1.50/M (90% off). Typical diagnosis with caching: $0.085. At scale (1000/day): $85/day, $2,550/month, $30,600/year. Target is <$0.50/diagnosis = <$500/day. We're at $85/day, so 5.9x headroom.

Reliability - Three main failure modes: 1) API timeout (5% of calls) - Solution: exponential backoff retry (95% → 99.95% success). 2) Invalid JSON (0.2%) - Solution: schema validation + self-repair (0.2% → 0.001%). 3) Rate limiting (at 60+ concurrent) - Solution: token bucket rate limiter (50 req/s, no 429 errors).

Monitoring metrics: Success rate 99.2% (99.95% after retries), P50 latency 6.2s, P95 latency 9.8s, P99 latency 24s (retries), Avg cost $0.087. All well within Atiya targets (90% accuracy, <60s latency, <$0.50 cost).
