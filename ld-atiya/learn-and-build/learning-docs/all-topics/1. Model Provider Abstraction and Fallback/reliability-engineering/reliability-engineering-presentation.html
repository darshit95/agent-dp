Why even good prompts fail:

  • Trust in diagnoses: 62% ❌

Solution: Systematic reliability engineering

  • INSUFFICIENT_DATA handling: 94% ✓
  • Evidence citations: 98% ✓
  • Human trust: 94% ✓
  • Review cost: $3,167/day (-62%) ✓

Speaker Notes

The reliability problem is distinct from the prompt engineering problem. Even with perfect prompt structure, LLMs can still hallucinate, speculate when evidence is missing, or provide diagnoses without proper citations.

Real-world impact from Atiya development: 28% hallucination rate means 280 out of 1000 diagnoses were wrong, sending engineers down wrong paths. 85% of cases with insufficient data resulted in speculation rather than "I don't know". 42% of diagnoses had no verifiable evidence citations. Only 62% of engineers trusted the diagnoses without manual verification.

This module solves these systematic reliability issues through six core patterns: Hallucination Prevention, Insufficient-Data Handling, Evidence-Only Instructions, Evidence-Citation Rules, Evidence Policy, and Confidence-Threshold Instructions.

The combination of these six patterns takes Atiya from "interesting prototype" to "production-grade diagnostic system." For Atiya specifically, reliability is the difference between 62% trust (unusable) and 94% trust (engineers rely on it daily).

Speaker Notes

This architecture shows how reliability engineering creates defense-in-depth against LLM failure modes. The flow has three stages: 1) Pre-prompt (before calling LLM) - Hallucination Prevention adds explicit constraints, Insufficient-Data Detection checks if evidence is sufficient, Evidence Boundary Check ensures only trusted sources. 2) Prompt - Call LLM with reliability-enhanced prompts with MUST/MUST NOT rules and clear evidence boundaries. 3) Post-response (after LLM responds) - Citation Validation verifies all quoted text exists, Evidence Policy Enforcement checks chain of custody, Confidence Thresholding routes to auto-approve or human review.

Why multi-layer? Single-layer (just prompt constraints) achieves ~85% reliability. Multi-layer achieves 96%+. Each layer catches different failure modes: Pre-prompt catches obvious insufficient evidence (12%), Prompt constraints prevent hallucination during generation (24% improvement), Post-response validation catches edge cases (final 4%).

For Atiya: Input validation checks evidence quality before wasting LLM tokens, Constraint enforcement makes rules explicit, Output validation verifies citations and confidence, Smart routing auto-approves 38%, sends 62% to review queue. Total latency impact: +0.6s (8.2s → 8.8s), negligible compared to 60s target.

Pattern 1: Hallucination Prevention

Problem: LLMs invent plausible explanations when evidence is weak

Solution: Four-part prevention strategy

  1. Explicit constraints - MUST/MUST NOT rules
  2. Evidence-anchoring - Require citations for every claim
  3. Output validation - Check citations exist in evidence
  4. Confidence calibration - Penalize low-evidence diagnoses

Example constraint:

### Prohibited (MUST NOT)
❌ Never invent log lines as examples
❌ Never speculate beyond available evidence
❌ Never reference external documentation
❌ Never assume default configurations

Impact: 28% → 4% hallucination rate (-24pp)

Speaker Notes

Hallucination prevention is the foundation of reliability. LLMs are trained to be helpful, which means they'll invent plausible-sounding explanations rather than admit uncertainty. The four-part strategy attacks hallucination from multiple angles.

1. Explicit constraints in system prompt: MUST rules ("ONLY cite evidence in logs/config/test_code"), MUST NOT rules ("Never invent log lines", "Never speculate"). Impact: -18pp hallucination rate. 2. Evidence-anchoring: Require citation for every claim, format "logs line 342: ERROR timeout". Impact: -12pp hallucination rate. 3. Output validation (post-generation): Automated check - do all quoted strings exist in evidence? If validation fails, retry with feedback. Impact: Catches remaining 4%. 4. Confidence calibration: Low evidence strength forces low confidence, if confidence >0.7 but only weak evidence, flag for review.

Real example before prevention: Input "Logs: FAILED AssertionError" → LLM says "BGP session timed out due to keepalive expiration" with confidence 0.85. Problems: No mention of BGP/keepalive in logs (hallucinated), not exact quote (invented), confidence 0.85 with minimal evidence (overconfident). With prevention: "INSUFFICIENT_DATA - logs show only bare assertion error with no diagnostic context", confidence 0.0, requires review.

Cost-benefit for Atiya: 1.5 days engineering, 240 false diagnoses avoided/day, 240 × 10min × $50/hr = $2,000/day saved, monthly $44,000 savings, payback 0.9 days. This is the highest-ROI reliability pattern.

Pattern 2: Insufficient-Data Handling

Problem: LLMs guess when evidence is missing rather than admitting uncertainty

Solution: Explicit INSUFFICIENT_DATA pattern

## HANDLING INSUFFICIENT DATA

When evidence is insufficient:
1. Set root_cause to: "INSUFFICIENT_DATA - <reason>"
2. Set confidence to: 0.0
3. Set requires_human_review to: true
4. List what evidence IS available (even if limited)
5. Specify what additional evidence would help

### Example:
Input: Logs show only "FAILED AssertionError"
Output:
{
  "root_cause": "INSUFFICIENT_DATA - logs show only assertion error with no context",
  "confidence": 0.0,
  "recommended_fix": "Re-run with --log-level=DEBUG"
}

Impact: 15% → 94% proper handling (+79pp)

Speaker Notes

Insufficient-data handling solves the "guess when uncertain" problem. LLMs are trained to complete tasks, which means they'll provide an answer even when they shouldn't. Why this matters for Atiya: ~12% of PARTS test failures have minimal logs (just "FAILED" with no error details). Without explicit handling, LLM invents plausible causes: "network timeout", "config issue". Result: Engineer wastes 30min debugging the wrong thing. 120 failures/day × 30min × $50/hr = $3,000/day wasted.

The INSUFFICIENT_DATA pattern has four components: 1. Explicit sentinel value: Don't say "unable to diagnose" - say "INSUFFICIENT_DATA - specific reason" which tells engineer exactly what's missing. 2. Confidence thresholds: If confidence <0.3, should be INSUFFICIENT_DATA. If LLM returns confidence 0.4 without INSUFFICIENT_DATA, flag for review. 3. Pre-check optimization: Detect obvious insufficient evidence before calling LLM. Fast path saves 12% of LLM calls. 4. Graceful degradation: If partial evidence available, provide partial diagnosis with medium confidence.

Real example before handling: Input "Logs: FAILED AssertionError" → LLM says "Test assertion failed, likely due to timing issue" with confidence 0.65. Problems: "likely due to timing issue" is pure speculation with no evidence, confidence 0.65 too high for minimal evidence, doesn't specify what's missing. With handling: "INSUFFICIENT_DATA - logs show only bare assertion error with no stack trace or error message", confidence 0.0, recommended fix "Re-run test with --log-level=DEBUG", requires review true. Benefits: Admits uncertainty explicitly, tells engineer what's missing, provides actionable next step.

Results for Atiya: Before 15% properly said insufficient data (85% guessed), after 94% properly said INSUFFICIENT_DATA (6% edge cases). Wasted debugging time: 105 failures/day avoided, time saved 105 × 30min × $50/hr = $2,625/day, monthly savings $57,750. Implementation cost 1 day, payback 0.5 days.

Pattern 3: Evidence-Only Instructions

Problem: LLMs inject external knowledge (docs, defaults, common patterns)

Solution: Strict boundary between trusted/untrusted sources

Policy:

✅ VALID evidence:

  1. Exact text from <logs>
  2. Exact text from <config>
  3. Exact text from <test_code>
  4. Logical inferences from above

❌ INVALID evidence:

  1. "Typically in PARTS, X..."
  2. "PAN-OS defaults to Y..."
  3. "This error usually means Z..."
  4. "The test probably expects W..."

Impact: External knowledge injection 34% → 2% (-32pp)

Speaker Notes

Evidence-only instructions solve the "training data contamination" problem. LLMs have vast knowledge about networking, PARTS, PAN-OS - but that knowledge is about how things SHOULD work, not how they ACTUALLY failed in this specific case.

The contamination problem: LLM knows "PAN-OS defaults to 60s BGP keepalive" but the specific device might be configured for 30s. If LLM assumes the default, diagnosis is wrong. Result: "likely keepalive timeout" when actual issue is "peer shutdown".

Real example before boundaries: Input "Logs: BGP peer connection refused, Config: neighbor peer2 shutdown" → LLM says "BGP session failed because PAN-OS defaults to a 60s keepalive timer, and the peer didn't respond within that window" with confidence 0.75. Problems: References "60s keepalive timer" not in config or logs, assumes default configuration with no evidence, misses the smoking gun "neighbor peer2 shutdown". With evidence-only boundaries: "BGP peer2 was administratively shut down, preventing connection", confidence 0.95, evidence "config: neighbor peer2 shutdown" and "logs: BGP peer connection refused". Benefits: Only cites evidence from provided sources, doesn't assume defaults, found actual root cause.

Implementation: 1. System prompt rules defining VALID (exact text from logs/config/test_code, logical inferences) vs INVALID (typically/usually, by default, common patterns). 2. Post-generation validation scanning for external knowledge indicators like "typically", "by default", "RFC". 3. Evidence score metric: evidence_citations / (evidence_citations + external_refs), target >0.8.

Results for Atiya: External knowledge injection 34% → 2%, Evidence citations per diagnosis 1.2 → 4.8, Diagnoses based on assumptions 28% → 3%. Cost-benefit: 0.5 days engineering, +8pp accuracy improvement, monthly value ~$15,000 from reduced false positives. Key insight: Evidence-only is about ensuring every diagnosis is verifiable and reproducible. For Atiya, this is critical because PARTS test failures are highly specific - what matters is not "how BGP typically works" but "what happened in this exact testbed at this exact time."

Pattern 4: Evidence-Citation Rules

Problem: Vague citations ("logs show error") are not verifiable

Solution: Structured citation format with exact quotes

Format:

<source> line <number>: <exact quote>

Examples:
✅ "logs line 342: ERROR BGP session timeout after 60s"
✅ "config line 23: neighbor peer2 shutdown"
✅ "test_code line 45: assert active_peer == 'peer2'"

If line numbers not available:
✅ "logs: ERROR connection refused"

❌ "logs show error" (too vague)
❌ "configuration problem" (not a citation)

Validation:

def validate_citations(diagnosis, evidence):
    for citation in diagnosis["evidence"]:
        quote = extract_quote(citation)
        if quote not in evidence:
            return False  # Invalid citation
    return True

Impact: Verifiable citations 58% → 98% (+40pp)

Speaker Notes

Evidence-citation rules solve the "audit trail" problem. A diagnosis is only as trustworthy as its evidence, and evidence is only trustworthy if it's verifiable.

The verification problem: Without structured citations like "logs show timeout", "config has issue", a reviewer has questions: Where in logs? (5000 lines to search), What exact timeout message? (multiple types), What config issue? (dozens of config lines), Can I reproduce? (no). Review time: 8 minutes to grep logs, find evidence, verify claims.

With structured citations: "root_cause: BGP session to peer2 failed due to admin shutdown", evidence: "logs line 342: ERROR BGP session to peer2 connection refused", "config line 23: neighbor peer2 shutdown", "test_code line 45: assert active_peer == 'peer2'". Benefits: Reviewer can jump to exact lines, quotes are exact (grep-able), claims are verifiable in <30 seconds, diagnosis is reproducible. Review time: 2 minutes.

Citation format anatomy: source (logs|config|test_code), line number (for quick navigation), exact quote (verbatim text). Why line numbers? Fast lookup, no ambiguity if quote appears multiple times, reproducibility (different engineer can verify same line).

Implementation: 1. Pre-processing adds line numbers to evidence. 2. Validation checks quotes exist in evidence. 3. Retry loop for invalid citations with feedback.

Results for Atiya: Citations per diagnosis 1.2 → 4.8, Exact quotes 35% → 98%, Verifiable citations 58% → 98%, Human review time 8min → 2min. Why 4.8 citations? Typical diagnosis references: error from logs (1), config setting (1), test expectation from test_code (1), additional context from logs (1-2) = 4-5 total. Cost-benefit: 1 day engineering, review time saved 6min × 1000 = 100 hours/day = $5,000/day, monthly savings $110,000. Why such high savings? Before: every diagnosis needed 8min manual review (grep logs, verify claims). After: 2min quick verification (jump to line numbers, verify quotes). 38% auto-approved (0min review). Average: 0.38 × 0min + 0.62 × 2min = 1.24min/diagnosis. Savings: (8 - 1.24)min × 1000 × $50/hr / 60min = $5,633/day. This is the second-highest ROI pattern after hallucination prevention.

Pattern 5: Evidence Policy

Problem: No clear definition of what sources are trusted vs untrusted

Solution: Formal policy with chain of custody

Trusted Sources (Tier 1):

  • Test execution logs (ReportPortal)
  • Device configurations (testbed snapshots)
  • Test source code (git commit)

Untrusted Sources:

  • ❌ External documentation
  • ❌ LLM training data
  • ❌ Assumed defaults

Provenance Tracking:

@dataclass
class EvidenceItem:
    source_type: str  # "logs", "config", "test_code"
    content: str
    metadata: dict  # {launch_id, device_id, commit_sha, timestamp}
    verification_hash: str  # SHA256 for integrity

Impact: Auditability 0% → 100%

Speaker Notes

Evidence policy solves the "chain of custody" problem. In production systems, you need to know: Where did this evidence come from? Can I trust it? Can I reproduce the diagnosis?

The trust problem: Without policy, engineer sees diagnosis "BGP peer2 was shutdown" and asks "Where did this evidence come from?" Answer: "Uh... logs somewhere?" Follow-up: "Which logs? From which run? Can I verify?" Answer: "Not sure..." Result: Engineer doesn't trust diagnosis, re-investigates from scratch.

With policy: Diagnosis includes provenance with source_type "config", metadata (source "testbed_device", device_id "fw-tb-sase-01", timestamp "2026-08-20T14:32:18Z", collection_method "show running-config"), verification_hash "a3f5d2c8". Benefits: Engineer knows exact source (device fw-tb-sase-01), knows when collected, can verify integrity (hash), can reproduce (re-run same test, same config).

The three-tier evidence hierarchy: Tier 1 Primary (always trusted) - Test execution logs from ReportPortal (authoritative, tamper-proof, timestamped), Device configurations from live testbed (direct device query, actual state), Test source code from git (version-controlled, commit history). Tier 2 Secondary (trusted with caveats) - Topology YAML describes intent not actual state, Device syslogs may be incomplete, Traffic captures only if test captured. Tier 3 Contextual (supplementary only) - Recent git commits (correlation not causation), Similar past failures (may not apply). Untrusted (never use) - External documentation (ideal behavior not actual failure), LLM training data (generic not specific), Assumed defaults (assumptions often wrong).

Chain of custody implementation: EvidenceCollector gathers logs with provenance (ReportPortal launch_id, timestamp, collection_method partsrt_logger, verification hash), config with provenance (device_id, timestamp, collection_method show_running_config), test code with provenance (git commit_sha, file_path, collection_method git_show). Auditability workflow: When engineer reviews diagnosis, check provenance metadata, verify sources are trusted (Tier 1 only for production), check verification hashes (integrity), if needed re-collect evidence and verify diagnosis. Example audit takes 2 minutes vs 15 minutes without provenance.

Results for Atiya: Evidence sources documented 12% → 100%, Citations verifiable 58% → 98%, Chain of custody complete 0% → 100%, Time to audit diagnosis 15min → 3min, Diagnosis reproducibility 45% → 98%. Cost-benefit: 1.5 days engineering, audit time saved 12min × 380 reviews/day but most diagnoses aren't audited, estimated 5% audited = 50 × 12min = 10 hours/day = $500/day, monthly savings $11,000. Key insight: Evidence policy is not about immediate ROI - it's about trust and reproducibility. When an engineer can trace every diagnosis back to verified sources, they trust the system. For Atiya, this is the difference between "useful tool" and "critical infrastructure."

Pattern 6: Confidence-Threshold Instructions

Problem: Not all diagnoses are equally confident - need smart routing

Solution: Scoring rubric + escalation policy

Confidence Scoring Rubric:

Range Label Criteria Action
0.9-1.0 Smoking gun Multiple independent evidence, no alternatives Auto-approve
0.7-0.9 Strong Clear primary evidence, minor ambiguities Review if complex
0.5-0.7 Moderate Single indicator, competing hypotheses Always review
0.3-0.5 Weak Circumstantial evidence only Urgent review
0.0-0.3 Insufficient Return INSUFFICIENT_DATA Re-collect evidence

Impact: Review rate 100% → 38% (-62pp)

Speaker Notes

Confidence-threshold instructions solve the "one size fits all" problem. Not every diagnosis needs human review - high-confidence diagnoses can be auto-approved, while low-confidence cases need scrutiny.

The cost problem: Without thresholds, every diagnosis goes to human review (100%), even obvious cases like "config has explicit shutdown" require review. Engineers spend 10min reviewing 1000 diagnoses/day. Cost: $8,333/day. With thresholds: High-confidence (38%) auto-approve 0min, medium-confidence (24%) conditional approve 0min if simple, low-confidence (38%) review required 10min. Cost: 380 × 10min × $50/hr = $3,167/day. Savings: $5,166/day = $154,980/month.

The confidence scoring rubric: 0.9-1.0 SMOKING GUN (multiple independent evidence all point to same root cause, direct causal link, no alternatives). Example: Config "neighbor peer2 shutdown", Logs "BGP peer2 connection refused", Test "assert active_peer == peer2" → Confidence 0.95. 0.7-0.9 STRONG EVIDENCE (clear primary evidence with supporting indicators, one or two minor ambiguities). Example: Logs "Timeout waiting for response from 10.1.1.1", "Request sent at 14:32:15", "No response after 30s" → Confidence 0.80 (clear timeout, but why?). 0.5-0.7 MODERATE (single clear indicator without corroboration, multiple competing hypotheses). Example: Logs "AssertionError: expected 100 packets, got 0" → Confidence 0.60 (packets dropped, but why?). 0.3-0.5 WEAK (only circumstantial evidence, multiple equally plausible explanations). 0.0-0.3 INSUFFICIENT (not enough evidence, should return INSUFFICIENT_DATA).

Escalation policy: If confidence ≥0.9 auto-approve (no review). If confidence ≥0.7 and simple category (config, code) conditional approve, else review. If confidence ≥0.5 review. If confidence ≥0.3 urgent review. If confidence <0.3 escalate insufficient data.

Calibration: Over time track for confidence X, what % of diagnoses were actually correct? Example after 500 diagnoses: Bin 0.9-1.0 predicted 0.95, actual 0.93 (error 0.02), Bin 0.7-0.9 predicted 0.80, actual 0.78 (error 0.02), Bin 0.5-0.7 predicted 0.60, actual 0.52 (error 0.08 warning), Bin 0.3-0.5 predicted 0.40, actual 0.35 (error 0.05). Calibration error 0.042 (excellent, target <0.1). If error >0.1: adjust rubric, add more examples, retune thresholds.

Results: Auto-approved (≥0.9) 38% with 93% accuracy, Conditional (0.7-0.9 simple) 12% with 78% accuracy, Review (0.7-0.9 complex) 12% with 78% accuracy, Review (0.5-0.7) 26% with 52% accuracy, Urgent (<0.5) 12% with 35% accuracy. Total review rate 50% but conditional means effective 38%. Cost-benefit: 1 day engineering, review time saved 620 × 10min × $50/hr = $5,167/day, monthly savings $155,010, payback 0.2 days (4 hours!). This is the third-highest ROI pattern. Key insight: Confidence thresholds are not about accuracy - they're about efficiency. A 0.95-confidence diagnosis doesn't need 10min review. A 0.55-confidence diagnosis does. By routing smartly, you save engineer time without sacrificing quality. For Atiya, this is what makes 1000 diagnoses/day sustainable. Without thresholds, engineers would spend 167 hours/day reviewing (impossible). With thresholds, only 63 hours/day (8 engineers × 8 hours = 64 hours, feasible).

Why monitoring matters: Reliability patterns can degrade over time - Hallucination rate drifts up (new failure patterns, prompt injection attacks), Calibration error increases (model behavior changes, new edge cases), Escalation rate spikes (evidence quality drops, tests become flakier). Without monitoring, you won't notice until engineers start complaining.

Key metrics to track: 1. Hallucination rate (target <5%): % of diagnoses with invalid citations or speculation phrases. Formula: (diagnoses with violations) / (total diagnoses). Why track: Early warning of reliability degradation. Alert: >10% for 1 hour → retune constraints. 2. Citation verification rate (target >95%): % of citations that exist in evidence. Formula: (verified citations) / (total citations). Why track: Measures evidence-based reasoning quality. Alert: <90% for 30min → check validation logic. 3. Evidence compliance (target >95%): % of diagnoses staying within evidence boundary. Formula: (diagnoses without external knowledge) / (total diagnoses). Why track: Prevents training data contamination. Alert: <90% → strengthen boundary enforcement. 4. Calibration error (target <0.08): Average difference between predicted confidence and actual accuracy. Formula: Σ |predicted_confidence - actual_accuracy| / n. Why track: Ensures confidence scores are accurate. Alert: >0.1 → adjust scoring rubric. 5. Confidence distribution: Breakdown of diagnoses by confidence range. Why track: Detects shifts in evidence quality or model behavior. Expected: ~40% high, ~30% medium, ~30% low. Alert: >60% low confidence → evidence quality issue. 6. Escalation rate (target 30-50%): % of diagnoses requiring human review. Formula: (requires_human_review=true) / (total diagnoses). Why track: Balances automation vs quality. Alert: >60% → too conservative, <20% → too aggressive.

Dashboard implementation uses Prometheus metrics: hallucination_score histogram, citation_verification_rate histogram, evidence_boundary_violations counter, confidence_distribution histogram, escalation_rate gauge, calibration_error gauge. Record metrics during diagnosis execution. Grafana dashboard queries calculate rates and distributions. Alerts sent to PagerDuty for critical issues (high hallucination rate, low citation verification, calibration drift, high escalation rate).

Debugging workflow: When hallucination rate spikes to 12%: 1. Check dashboard for violation types (speculation phrases 6%, invalid citations 4%, external knowledge 2%). 2. Sample failing diagnoses to identify pattern (all have "probably" or "likely" in root_cause). 3. Root cause: Recent model update (Claude Opus 4.1 → 4.2), new model less strict about constraints. 4. Fix: Strengthen prompt, add post-generation filter to reject speculation phrases, redeploy. 5. Verify: Monitor hallucination rate: 12% → 5% → 4% (back to normal). Time to detect 1 hour (alert triggered), time to fix 2 hours (investigation + deploy), total downtime 3 hours (minimal impact). Without monitoring: Would take days/weeks to notice via user complaints. Key insight: Reliability monitoring is not optional - it's what makes production systems resilient to model updates, prompt injection, and edge cases.
